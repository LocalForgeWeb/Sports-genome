# Backend V1 contracts

Calculation and data contracts, mapped to the code that implements them (brief §3–§8, B039–B047). A contract is added here only when it describes real code; proposals live in `decisions.md` until implemented.

## Logged weights and units (B024, B025, B048, B243)

**Code.** `client/src/lib/deviceWorkoutLog.ts` (`DeviceSetLog.unit`, `DeviceWorkoutSession.weightUnit`, `setWeightUnit`, `setWeightKg`, `weightInUnit`, `stampLegacyWeightUnits`), `workoutStrengthRecord.ts`, `useAthleteSync.ts`, `setEntryFields.ts`, `components/DeviceWorkoutTracker.tsx`.

- **What is stored.** Each set keeps the weight exactly as typed (a string) and the unit it was typed in. The session keeps the unit it started with. Both are the athlete's submission; nothing normalised is stored in their place.
- **Which unit.** A session takes the profile's unit when it starts and keeps it until it ends; the weight box is labelled with that unit. Changing the profile's unit mid-workout does not change a running session.
- **Resolution order.** set.unit → session.weightUnit → the caller's fallback (the profile's unit). The fallback is reached only by history not yet stamped (see D-005).
- **Normalisation.** kg = value × 0.45359237 when the unit is lb, the value itself when kg. Exact constant, no intermediate rounding. Rounding happens only for display (1 decimal) and for a carried-forward box value (0.01).
- **Comparisons.** The heaviest set of a session is chosen by kilograms, so a session that mixed units still finds it.
- **Sync.** A lift is sent to the account as typed, in the unit it was typed in (`reportedLoad`, `reportedUnit`); `load_kg` is generated by Postgres.
- **Equivalence.** 100 kg and 220.46226218487757 lb give the same kilograms within 1e-9 (`deviceWorkoutLog.units.test.ts`).
- **Not yet.** Load convention (total vs per hand) and added-load semantics for bodyweight exercises are still implicit (`loadSemantics: "total_external_load"` for every lift) - EN-07/EN-09, B049.

## Counts (B155, B156, B265)

**Code.** `deviceWorkoutLog.ts` (`isCompletedSet`, `isCompletedWorkout`), `athleteRecord.ts` (`recordedLifts`, `summarizeAthleteRecord`, `deviceSessionsAsTraining`), `liveSession.ts` (`trainingStateByDayLabel`), `ProgressOverviewPanel.tsx`, `TodayActionPanel.tsx`.

| Term | Definition |
|---|---|
| Completed set | A set the athlete marked done and did not skip. A planned set is never a completed set. |
| Completed workout | A finished session holding at least one completed set. Finishing with nothing logged ends the session and records nothing. |
| Logged lift | One per exercise per completed workout - its heaviest completed set with at least one rep - plus each typed test. A completed set with no reps is a set, not a lift. |
| Whose records | Typed lifts: the device's while the app runs on the device stores (`directAccess`), otherwise the account's. Workouts: the device's always, plus the account's sessions when the account is the source. Lifts carried from device workouts are always included. Home, Progress and Strength apply the same rule. |
| This week | Completed workouts whose finish falls on or after the start of the current training week, and their completed sets. |

## Active workout (B154, B158)

- One active session per device. Start re-reads storage and picks up a session already running (another tab, a reload) instead of opening a second.
- Every change to a running session is applied to the copy in storage at that moment, so a set logged in another tab is kept. Another tab's writes are picked up through the `storage` event.
- A session finished or removed elsewhere takes no further changes here and closes with a notice; Finish reads the stored copy, so it includes sets logged in another tab and cannot complete a session twice.
- Local durability only. Account sync states are batch 6 (B169, B176).
