## 1. Why a schema of its own, and who reaches it

`public` has open default privileges in this project (every new table there is granted to `anon` and `authenticated`), so the atlas lives in `specialization`, which has none (checked read-only on 16 Oct: no global default ACLs exist). The schema is **not** in the Data API's exposed schemas, so PostgREST cannot serve it, and `pg_graphql` is not installed in the project. Inside the database everything is revoked from `PUBLIC`, `anon`, `authenticated` and `service_role` and then granted narrowly (§5), so the grants are correct even if the schema is exposed one day.

Today nothing reads or writes it: the page reads the TypeScript content in its bundle and keeps goals and measurements on the device. The database copy exists so that a server-side summary, a later sync of goals and measurements, and the owner's own queries all read the same reviewed content the app counts with.

## 2. No exposure ledger

The brief's `exposure_ledger` is not created. Workouts, sets and drop-set stages live in `localStorage`; Supabase has no session, set, bout or segment table, so a ledger row's `source_bout_key` would point at nothing: the "dangling key" the brief forbids. Exposure is calculated on demand on the device from the records Home, Plan, Review and Progress already read (`06-calculation.md`). When bouts reach a server table, a ledger can be added with real composite keys to it.

## 4. Rules the database enforces

**Anatomy.**
- A node cannot become its own ancestor: a trigger walks up from the new parent (not only the self-parent CHECK). Parent changes take a transaction-scoped advisory lock, so two concurrent changes cannot each pass and together close a loop.
- A node action rests on a function claim of its own node (the composite foreign key above); turning that claim into another kind is refused too.

**Mapping versions: draft → published → retired.**
- A version is inserted as a draft, filled, then published by `update ... set state = 'published'`. Inserting one already published is refused.
- A draft may change freely and may be deleted. A draft cannot be retired (delete it).
- Once published, the version row, its mappings and their sources are immutable, for every role, the owner included. Its state may only move to `retired`. Published and retired versions cannot be deleted. Changing mappings means a new version key; the app chooses its version explicitly and never adds versions together.
- What the version rests on is frozen with it (next list).
- Row inserts are checked after the write, so an upsert that changes nothing (the seed applied again) never trips the guard; updates and deletes are checked before. The guards lock the version row `FOR SHARE`, so a publish running at the same moment as an insert waits for it, and its check then sees the row.

**What a published version rests on.** A version is more than its rows: a variant's `deliberate_hold` decides whether a direct isometric mapping counts as a deliberate hold (cat-403's FDS and FDP), the publication rule rests on the muscles' reviewed status, function claims and node actions, and users read the claims and sources behind every row. While any published **or retired** version depends on one of these rows, triggers refuse, for every role and the owner too:
- any change to, or deletion of, an `exercise_variants` row one of its mappings uses (an update that changes nothing passes);
- any change to, or deletion of, a `node_actions` row whose node and action one of its mappings names;
- a mapped muscle (`nodes`) leaving `reviewed`, or being deleted, or, while reviewed, a change to its `region_id`, `role` or `catalog_muscle_key`: they decide what its work counts toward (the calculator counts a muscle's bouts in the region total only when its region is the region's, and reads the catalog keys of the region's target muscles to decide which unmapped, catalog-tagged work is region work). Its names, descriptions, kind, parent and `database_muscle` (which follows `public.muscles` on update) may still be edited; a draft muscle, which only draft rows can map (rule 6), stays free until it is reviewed;
- on a **reviewed** claim of a mapped muscle: a change of key, node, kind, statement or basis (the provenance label users read beside it: established anatomy, experimental, anatomical inference, product assumption), a review status other than `reviewed`, or deletion; its review date and note may still be edited. A draft or rejected claim was never shown or relied on (rule 8 keeps every reviewed mapping off one; only a draft row may rest on it) and stays free; a new claim may be added and reviewed, and is then frozen like the rest;
- adding, changing or removing a `claim_sources` row of such a claim;
- a change to the `source_key`, `url`, `title` or `evidence_type` of a source its mappings or such claims cite, or deleting it; its DOI, retrieval date and notes may still be edited.

Not frozen, and why: a node no published version maps (the anconeus and the two compartments in `forearm_mappings_v1`) keeps its region, role and catalog key editable, and a new node may be added. *(Schema v1's text, 16 Oct; since schema v2 the calculator reads the region's own `catalog_keys` and `region_only_tag_scope`, which `guard_published_region` freezes once a version of the region is published, §10, so a new target muscle no longer changes what counts as region work.)* Under v1 the calculator read the catalog keys of **every** target muscle of the region (`regionCatalogKeys`, `06-calculation.md` §2 "Region"), so making the anconeus a target, or adding a target muscle with a new catalog key, would have changed which unmapped, catalog-tagged work counts as region work. Refusing that would mean refusing new nodes. Nothing counts from the database today; a server-side summary must read the region's nodes as they were when the version it counts under was published, or a node freeze per region must be added first.

A new record is always allowed: a new variant, node action, claim or source (only a frozen claim's own list of sources is closed, as above). A changed one needs a new key, and where mappings must point at it, a new mapping version. A claim found wrong after publication therefore stays as published and readable, in the content as well (the seed refuses content that drops it, §7); the correction is a new claim under a new key (§9). Publishing locks every row the version will rest on `FOR SHARE` before it checks the rule, so a change made at the same moment either commits first (and the check sees it) or waits and is then refused; the one guarded insert (a claim's source) locks the versions instead, like the mapping guards.

**TRUNCATE** fires no row trigger, so a statement-level `BEFORE TRUNCATE` trigger on `mapping_versions`, `variant_mappings`, `mapping_sources`, `rule_versions`, `exercise_variants`, `nodes`, `node_actions`, `claims`, `claim_sources` and `sources` refuses it while a published or retired version exists (`rule_versions`: while a published rule exists), `TRUNCATE ... CASCADE` from another table included. A database holding only drafts can still be cleared. The service role holds no TRUNCATE privilege at all (§5).

**The publication rule** (`specialization.mapping_version_problems(version_id)`, callable by the service role to check a draft first; the trigger runs it on publish). A version is published only when:
1. it has at least one mapping;
2. no mapping is `rejected` (rejected rows are removed before publishing; they are not history);
3. every mapping, reviewed **or draft**, has at least one source;
4. every reviewed mapping has a source with a locator (where in the source);
5. every mapped muscle has a reviewed function claim;
6. every muscle a reviewed mapping credits is itself reviewed;
7. every mapping that names a joint action names one its muscle performs (a `node_actions` row, so it rests on that muscle's function claim);
8. the function claim behind a **reviewed** mapping's node action is itself reviewed;
9. and it has at least one source (`claim_sources`).

Rules 5 to 9 together: a reviewed mapping a user reads always rests on a reviewed muscle, a node action and a reviewed, sourced function claim that the user can read too (RLS shows node actions and claims only when the claim is reviewed). Publishing then freezes that claim, its basis and its sources with the version (above), so what the mapping rests on cannot be rejected or rewritten afterwards. A draft row's node action may still rest on a draft claim: the row is never shown or counted. Rule 9 asks for a source on the claim itself, although the brief allows a citation at the claim **or** the mapping level: the function claim is what says the muscle performs the action, and every forearm claim already has one (all 413 reviewed forearm rows pass 8 and 9).

**Draft rows in a published version are allowed.** `forearm_mappings_v1` is published with 413 reviewed rows and 5 drafts (`cat-144`, `cat-145`, `cat-299`, `cat-409` → FPL; `cat-317` → brachioradialis). A draft row keeps its source and its pending-review label; RLS never shows it to a signed-in user, and the calculator never counts it (it appears as "pending review"). Reviewing one of them later means publishing `forearm_mappings_v2`, because v1 is frozen with them as drafts. Rule 7 is the content lane's own test made strict: that test only checks the action when the muscle has node actions at all; here an action must always be one of the muscle's node actions (all 418 forearm rows pass).

Not enforced at publication: a diagram link per mapped muscle. The diagram is optional (null until drawn) and the page has a list alternative, so a missing drawing must not block counting.

**Rule versions.** A rule version is published when `published_at` is set; from then on it can neither change nor be deleted.

**Goals.** Exactly one of muscle or movement; `ends_on >= starts_on`; `target > 0` and `<= 10000` (the device's `GOAL_TARGET_SANITY_MAX`, a typo guard; it also refuses NaN and infinity); the time zone must be in `pg_timezone_names` (trigger, on insert and on a zone change); and the exclusion constraint `goals_no_overlap` (btree_gist) refuses two goals for the same user, region, muscle-or-movement, side, metric and period whose date ranges share a day (`daterange(starts_on, ends_on, '[]')`, an open end runs forever; the muscle and movement ids are prefixed so they can never compare equal). An exclusion constraint holds under concurrent inserts, which a check before the write does not.

**Measurements.** `value > 0` and finite; `protocol` must be the device's `MeasurementProtocol` object: a non-empty `landmark`, `distanceFromLandmarkCm` null or ≥ 0, `posture` and `condition` from the app's lists, `device` null or text, `timeOfDay` null or `HH:MM`, and no other keys.

| `mapping_sources` | — | select: sources of those rows | select, insert, update, delete |
| `rule_versions` | — | select: published | select, insert, update, delete |
| `goals`, `measurements` | — | select, insert, update, delete: own rows only; update has USING and WITH CHECK | select, insert, update, delete (bypasses RLS) |
| `mapping_version_problems()` | — | — | execute |
| every other function | — | — | — |

- RLS is on for every table. Owner policies use `(select auth.uid()) = user_id`, evaluated once per statement.
- No reference table grants insert, update or delete to `authenticated`.
- The service role has exactly select, insert, update and delete: not TRUNCATE (it would skip every row guard), TRIGGER or REFERENCES. The writes it has are still bound by the immutability triggers (§4).
- No `SECURITY DEFINER` function exists; every function pins `search_path = ''`.
- Trigger functions need no execute grant: Postgres checks that when the trigger is created, not when it fires.
- **A new function is executable by everyone until revoked.** Postgres gives `PUBLIC` EXECUTE on every function it creates, and `alter default privileges in schema ...` cannot take that away (per-schema defaults only add to the global ones), so nothing here relies on default privileges. The schema file's `revoke all on all functions in schema specialization from public, anon, authenticated, service_role` covers the functions it creates; **a later migration that adds a function (the planned summary RPC, for one) must revoke it from `public, anon, authenticated` itself and grant only what is meant.** `server/specializationSchema.test.ts` walks `pg_proc` with `aclexplode` (a NULL `proacl` counts as the default, PUBLIC EXECUTE) and fails when PUBLIC, `anon` or `authenticated` can execute any function in the schema outside its allow-list, which is empty today.

## 7. The seed and its drift guard

As written for seed v1; §11 says what seed v2 changed. `emit-seed.ts` reads `specializationRegions` (production regions only) and `exposureRuleV1`, checks every reference resolves (claims → nodes and sources, node actions → a function claim of that node, mappings → variant, node, action and sources, parents without cycles, shared keys without conflicts), and writes SQL:

- **Upserts keyed by the content's own keys**, `on conflict ... do update ... where (row) is distinct from (new row)`: applying it again touches no row (tested by comparing every row's `xmin` and `ctid` before and after).
- **Lookups by key with LEFT JOINs** for rows that point at other rows (claim sources, node actions, mappings, mapping sources): a key the database lacks becomes a NULL in a NOT NULL column and fails the whole migration rather than dropping a row.
- **Mapping versions** go in as drafts, get their rows and sources, then `update ... set state = 'published' where ... and state = 'draft'`, so the publication rule runs on the real rows. A version already published is left alone; changed content under its key, or under a variant, node action, claim (its basis included) or source it rests on, or a mapped muscle's review, region, role or catalog key, is refused by the database (§4), and the whole seed rolls back with the database's message, including unrelated changes in it (tested for each kind of row). The nodes upsert writes every column, so a changed role reaches the guard and fails with "node forearm.fdp is mapped by mapping version forearm_mappings_v1 (published); it must stay reviewed and cannot be deleted, and its region, role and catalog muscle key, which decide what its work counts toward, cannot change. Add the changed muscle under a new id and map it in a new version".
- **Sets the content owns end up exactly as the content has them**: a mapping version's mappings and their sources; the claims of the regions in the seed (a claim key carries its region, `forearm:…`), with their sources and the node actions resting on them; and a diagram asset version's views, paths and labels. Rows the content no longer has are deleted before the upserts (a drawing's views after its paths and labels: views are written first, so a path may move to a new view in the same seed, and a view is deleted once nothing is drawn in it), so a removal under a published version is refused like any other change (the seed fails naming the mapping, node action or claim), and a draft version or a draft claim is cleaned. Node actions go first and are matched by node, action and claim, so a draft claim can change kind, or a node action move to another claim, in one seed. Claims whose key names a region not in the seed are left alone.
- **It never deletes the records others point at**: regions, nodes (goals may point at one), actions, sources, catalog exercises and variants. A source or variant the content drops therefore stays in the database; one a published version rests on could not be deleted anyway.
- **Diagrams are optional.** A region without a drawing seeds none and the seed says so in a comment. The forearm drawing (`forearm_schematic` v1, 3 views, 127 paths, 28 labels; `08-diagram.md`) is seeded from `diagram.generated.ts`. Its views go in with their button words and order (`viewOrder`: Palm, Back, Thumb side); paths and labels are written in key order with whatever ids the drawing uses. The generator refuses an id the database would, a view without words, and a `viewOrder` that is not exactly the views drawn. The test reads each drawing back whole (views in order, every layer's paths and labels) and compares it with the content: the forearm's, and the deltoid fixture's front, side and rear, then a redraw that drops the rear view, renames and trims the side view, then one that moves every path to a new view, and back.
- **Regions** carry the page's words and measures (§3); a reference region is written with none.
- **Deterministic**: rows sorted by key (nodes parents first), no dates or counters from the run, region order irrelevant. Dollar-quoted text, with a tag chosen so no text can close it early.
- **Catalog links**: `supabase_exercise_id` is the `public.exercises` row with this catalog id under `source_repository = 'LocalForgeWeb/Sports-genome'` (unique by that table's own constraint), else the single row whose `canonical_name` ends `__catalog_<id>`, else null. In production on 16 Oct this resolved **103 of the then 117** catalog ids (the suffix alone would resolve 87; 16 rows such as `low_cable_row` carry the id without the suffix). The unresolved are the new forearm rows from 401 (401–416 today, 16 rows, with the wrist roller's 415 and 416), which are not in `public.exercises` yet; re-applying the seed links them once they are.
- **Size**: about 730 KB, mostly the 934 mapping-source rows with their locators and limitations, and the key lists the stale-row deletes keep.

What it carries today: 2 regions (`forearm`, reference `upper_arm`), 24 nodes, 20 actions, 38 node actions, 60 claims with 115 claim sources, 71 sources, 119 catalog exercises, 119 variants, `forearm_mappings_v1` published with 418 mappings (413 reviewed, 5 draft) and 934 mapping sources, 1 diagram asset (`forearm_schematic` v1, 3 views), rule `specialization_exposure_v1`.

**S9** (the backend's row-level security guide, brief §13) was removed from the forearm region's sources on 16 Oct: nothing in the region data cited it, it is not anatomy evidence, and its title named the backend vendor in athlete-facing source lists. It remains this document's implementation reference: https://supabase.com/docs/guides/database/postgres/row-level-security.

**Drift guard.** `server/specializationSeed.test.ts` runs the generator in memory and fails, naming the first differing line, unless the committed seed is byte for byte its output. Any content change (a node, a claim, a mapping, the rule, the drawing) therefore needs `npx tsx scripts/specialization/emit-seed.ts` and a commit of the regenerated file.

## 8. Tests and how faithful PGlite is

PGlite 0.4.6 runs Postgres **17.5** in WASM (production is 17.6); 0.5.x moved to Postgres 18, so the version is pinned. **Changed tables.** Each replaced CHECK is dropped and added again, which validates the rows without writing them; a column added with a constant default writes no row and fires no trigger.

- `regions` gains `side_model` (`paired`, `midline`), `side_limb` (`arm`, `leg`), `side_word` and `side_word_plural` (the limb the logger asks about, as the page names it: "arm", "arms"; "side", "sides" on the chest and back), `catalog_keys` (the catalog muscle keys whose tagged work is the region's, stated rather than derived from its target muscles), `region_only_tag_scope` (`any` or `primary`, default `any`), `external_heading` ("Forearm muscles credited here": what another region's page puts over this region's muscles) and `measurement_defaults` (a JSON object, `{"<metric>": {"landmark": …, "posture": …}}`) and `on_side_template` (the region and a side in a sentence, `{side}` standing for left or right: "your {side} forearm"; a midline region's names no side, "your core"). The rule is an AFTER trigger on the stored row (`regions_sides_shape`), not a CHECK, because Postgres evaluates a CHECK on the row an upsert proposes before it finds the conflict (tested): seed v1, which upserts the forearm row without naming these columns, would otherwise be refused while leaving the row as it is. The rows already there are checked once when the file applies, and the file refuses itself if one fails. `measurement_metrics` may name `girth_cm`.
- `diagram_assets.sides`: `one_side` (drawn for the subject's right side, mirrored for the left) or `both_sides` (drawn whole, never mirrored: a midline region's). Null reads as `one_side`; the forearm's drawing leaves it out, so its published file stays byte for byte.
- `exercise_variants`: `laterality`, `forearm_orientation` and `wrist_position` accept `not_applicable` (the hands do no work, or a forearm column does not apply). No row changes; v1's 119 stay frozen.
- `variant_mappings.side_relation`: `same` (default; every `forearm_mappings_v1` row), `opposite` or `both`.
- `goals`: side `left`, `right` or `midline`; `(region_id, node_id)` → `region_nodes` (`goals_node_in_region`) and `(region_id, action_id)` → `region_actions` (`goals_action_in_region`), so a membership or region action a goal names cannot be deleted. A trigger (`goals_check_target`) holds what a goal may name: side `midline` exactly in a midline region; a new goal, or one moved to another muscle or movement, names a muscle its region lists as a target, or a movement its region lists, in a region with a page (`production`, or `fixture` in tests). A `reference` region lists muscles and movements but has no page and no Targets editor, so it takes no goal ("region upper_arm has no page yet"); in wave 0 every membership and region action a goal can name is then one schema v2 backfills, which is what lets the undo be followed by schema v2 again (below). A goal already stored on anything else (an adjacent or external member, one no longer listed, or one in a region without a page) stays and may only be ended or deleted: its end date set, kept or brought forward (with `updated_at`), never moved later or back to open, as `onlyEnds` in `shared/specialization/goals.ts` allows. It runs as the caller, so a signed-in user is checked against the memberships RLS shows them, and it applies to the service role too (a later sync). Because a muscle goal must name a listed target of its region, its region is the muscle's home, so `goals_no_overlap` is in effect keyed by muscle. A goal is ended with an UPDATE: an upsert's proposed row is checked as a new goal.
- `measurements`: side `left`, `right` or `midline`; metric `girth_cm` beside v1's two; `measurements_side_metric`: side `midline` exactly when the metric is `girth_cm` (a girth goes around the trunk; every other measure is of one limb); the protocol rule accepts the postures `arm_flexed` and `standing_relaxed`.
- `nodes.role`, `nodes.sort_order` and `actions.sort_order` carry comments saying they are v1's values and readers use `region_nodes` and `region_actions`.

**What a published version rests on, continued** (§4's list gains three rows; for every role, the owner too, and an update that changes nothing passes):
- a **membership** that a published or retired version of its region maps keeps its role, stays listed and is not deleted; its order and caveats may change. Rule 10 reads it and the page lists and credits the muscle by it. A membership no published version maps is free, and a membership may always be added (the shoulders listing a back muscle once the back ships). The seed never deletes a membership or a region action: goals point at them (a delete under another user's goal fails on that goal's key), so a dropped one is unlisted;
- an **attribute** is frozen from the publish of a version that maps its variant: `guard_mapping_version` sets `frozen_at` on the attributes the version's variants have at that moment, and from then the attribute is not changed or deleted. Until then it is free, so an attribute added after a version was published (any attribute on the 119 variants `forearm_mappings_v1` maps, which was published before attributes existed) stays correctable until the next publish of a version that maps its variant, and rule 11 makes sure that version's counting attributes are there. The only write that sets `frozen_at` is that publish's: from null to a time with nothing else changed, made by `guard_mapping_version`'s own UPDATE. The attribute guard holds it so: it refuses `frozen_at` set by any other UPDATE (it accepts it only one trigger deep, `pg_trigger_depth()` 2, which is where that UPDATE runs it) and an attribute inserted frozen, for every role, the owner included, since an attribute frozen with no version resting on it could never be corrected or dropped. The seed never writes `frozen_at`, so applying a seed again leaves it as it is;
- a **region** with a published or retired version keeps its status (a production region stays one), side model and limb, catalog keys and region-only tag scope, which decide what counts there, and is not deleted. Its words, order and measures may change.

TRUNCATE is refused on `region_nodes` and `variant_attributes` as on v1's frozen tables (§4), by the same trigger function.

**The publication rule, rules 10 to 13.** `mapping_version_problems` and `guard_mapping_version` are restated in full (`create or replace` keeps their grants: execute on the first for the service role only). A version is published by changing its state alone (and `published_at`): the rules read the stored draft, so `guard_mapping_version` refuses a publish that also changes the version's key, region or notes ("change its key, region or notes while it is a draft, then publish it"). Without that, a draft of the upper arm's muscles published with `region_id = 'forearm'` in the same statement passed rule 12 as the upper arm's and was stored as the forearm's (tested both ways).
10. Every mapped muscle is a listed member of the version's region.
11. Every mapped variant has the counting attributes its region's side model reads: `sided_by` always; `leg_laterality` in a leg-paired region or where `sided_by` is `leg`; `side_anchor` where a leg-paired region maps a `unilateral` or `either` leg variant, or where `sided_by` is `leg`. And a mapping on a variant that does not use the region's limb (`laterality` `not_applicable` in an arm region, `leg_laterality` `not_applicable` in a leg region) counts on both sides (`side_relation = 'both'`).
12. Every mapped muscle's home is the version's region: a region credits another region's muscle as that region's own versions do (`10-multi-region.md` §4.2), never through a mapping of its own.
13. The version's region has a page (`production`, or `fixture` in tests): "region upper_arm has no page yet (reference): promote it before publishing a version of it". Publishing freezes a region's status (the region guard below), so a version published in a reference region would keep it from ever being promoted, and a published version is never deleted. Seed v3 writes the upper arm's promotion before its versions section, so wave A publishes `upper_arm_mappings_v1` in a production region.

Rules 11 to 13 are read only while the version is a draft. The trigger runs the function before the publish is written, while the stored row is still a draft, so they bind every publish from schema v2 on and never re-judge a version already published. `forearm_mappings_v1` maps the biceps and brachialis, whose home is the upper arm, and was published before attributes existed; it passes rules 1 to 10, so `mapping_version_problems` stays null for it, and §9's read-only check still holds. Publishing a forearm draft that maps the biceps is refused with "mapped muscles whose home is another region: upper_arm.biceps".

**Publishing locks.** At the draft-to-published change, before it checks the rule, `guard_mapping_version` takes `FOR SHARE` on the version's region row (rule 11 reads its side model, and the region guard freezes it once the version is published), then on the version's memberships and on its variants' attributes, then on v1's list (variants, nodes, node actions, claims, claim sources, sources). After the check it stamps `frozen_at`. So a change to any of them either commits first, and the check sees it, or waits for the publish and is then refused. PGlite is one connection (§8), so the test reads the order from the function's text; the race is reasoned, not run.

## 11. Seed v2: every registered region (19 Oct 2026)

`supabase/migrations/20261019120100_specialization_atlas_seed_v2.sql` is the current seed. `emit-seed.ts` writes it from `registeredRegionContents` (every production and reference region, each as its folder declares it) and the published rule versions, as one full, idempotent re-emit (`10-multi-region.md` §5.2). It applies after schema v2 and is written against it. Not applied yet: it goes with schema v2 in wave 0's release, and is history from the moment production records it; each later release gets the next file (seed v3 with wave A, and so on), never an edit of this one. §7 still describes how the SQL is built (upserts that skip unchanged rows, lookups by key, versions published after their rows, the sets the content owns, determinism); what changed is below.

**Records, each written once.** A node is written from its home region's record; an action, source or variant from the shared libraries (`actions/`, `sources/`, `variants/`), so two regions that list one list the same record. The emitter refuses a node kept outside its home, a node that is not a member of its home region, and a key that means two different things. References (claims, node actions, mappings, memberships) are checked against the merged sets of every region in the seed, not region by region. `nodes.role` is written as `storedRole ?? role`: the role in the home region, except on `upper_arm.biceps` and `upper_arm.brachialis`, which keep the `external` seed v1 stored, for good (`10-multi-region.md` §1.3).

**Claim keys** come from the claim's owner (`claimKeyOf`: `<ownerRegionId>:<claim id>`), wherever its record is kept: the four forearm claims on the biceps and brachialis are now kept in `regions/upper_arm/claims.ts` and keep their `forearm:` keys. The stale-claim delete is computed over all the claims of every owner in the seed, so moving a record to another folder changes no row (tested). Seed v1's 60 claim keys and 38 node-action claim keys come out byte for byte, in seed v1's order (tested against seed v1's text and its database).

**Legacy sort orders.** `nodes.sort_order` and `actions.sort_order` are legacy since schema v2 (readers use the memberships and region actions). Every v1 row keeps the value seed v1 wrote (`v1SortOrders` in the emitter, checked against seed v1's database and its text, and the emitted text checked to name the same value for every v1 row, with the regions as registered and with a region sorting before the forearm). The pin matters only to a database that has not run seed v1, since the column is insert-only and every database runs seed v1 first; it keeps the emitted text saying what production holds. A new node gets its home region's sort × 1000 + its place among the home's members; a new action, the lowest region sort × 1000 + its place among the actions of a region listing it (`shoulder.flexion` 8003 and `shoulder.extension` 8004, from the upper arm at sort 8). Both are written when the row is inserted and never rewritten, so a region added later, wherever it sorts, cannot reorder rows already there.

**Memberships and region actions.** Each region's members go to `region_nodes` as `resolveMembers` gives them: the role derived from the member's home (its home role at home, `external` anywhere else), the member's order and caveats, `listed`. Each region's actions go to `region_actions` in its order. The forearm's 21 memberships and 20 region actions that schema v2 backfilled are written exactly as it wrote them (the 19 targets and the two externals in v1's node order with no caveats; the actions in v1's order), so they are not touched. The seed adds the forearm's two compartments (`group`) and the anconeus (`adjacent`), the upper arm's biceps and brachialis (`target`), and the upper arm's five actions. The upper arm is a reference region, so these are written from wave 0, not at its promotion (`10-multi-region.md` §5.3 expects upper_arm/target "from wave A"); it has no page, so it takes no goal (§10). Neither table loses a row to the seed: a member or action the content drops is set `listed = false` (refused for a member a published version of the region maps) and listed again when it returns. A delete would fail on another user's goal, or, with a cascade, delete their goals (tested with user B's goals on a dropped member and a dropped action).

**Regions.** Every column is written. A production or fixture region's row is its record, schema v2's columns included: the side model and limb, the side words, the side sentence (`on_side_template`), the catalog keys, the tag scope, the external heading and the measure defaults, in the shape schema v2 wrote the forearm's (`{"<metric>": {"landmark": …, "posture": …}}`, the shape of `measurementDefaults` in `types.ts`). The forearm's values equal what schema v2 wrote, so its row is not touched. A reference region has no page: until its promotion, schema v1's columns stay what seed v1 wrote for the upper arm (the label "Upper arm" and the status; no heading, entry label, words or measures; sort 0; no keys), and only schema v2's come from its record (paired by arm, "arm" and "arms", "your {side} upper arm", `{biceps, brachialis, triceps}`, `primary`, "Upper-arm muscles credited here", the mid-upper-arm circumference default). The promotion in wave A is then the one change that writes the rest. The emitter refuses a region the sides rule would refuse (§10), the side sentence included.

**Variant attributes.** The vocabulary goes first (`variant_dimensions`, `variant_dimension_values`, from `variants/dimensions.ts`): the counting dimensions with the exact ids and values rule 11 reads (`sided_by`: arm, leg, none; `leg_laterality`: bilateral, unilateral, either, not_applicable; `side_anchor`: working_leg, front_leg, stance_leg, top_leg, bottom_leg), then `10-multi-region.md` §3's descriptive set (knee, hip, torso, bench, plane, grip_width, stance, range). Then the attributes, each variant's counting ones always written out; the emitter refuses a variant without `sided_by` and a value outside the vocabulary. In wave 0 that is `sided_by` on all 119 forearm variants: `arm` where `laterality` is not `bilateral`, `none` otherwise, which is how the logger and the calculator read them today. All of it is written before the versions section, so a version the same seed publishes freezes the attributes it rests on. A seeded variant's attributes are a set the content owns, like a version's mappings: an attribute the content no longer gives the variant is deleted before the upsert, so a later publish never freezes a counting attribute (`leg_laterality`, `side_anchor`) that the calculator and the logger no longer read; a frozen one is refused by name ("attribute … of variant … is frozen"), and nothing of that seed is applied. A variant the seed does not hold keeps its attributes. The seed writes `variant_key`, `dimension_id`, `value` and `notes`, never `frozen_at`, and never deletes a dimension or a value. `forearm_mappings_v1` was published before attributes existed, so its variants' attributes stay unfrozen until a later version maps them.

**Mappings, drawings and the rule.** Every mapping writes its `side_relation`: `same` on each of `forearm_mappings_v1`'s 418 rows, which changes nothing, since schema v2's default already says so. **The header** names schema v2 without its version digits ("Applies after schema v2 (…_specialization_atlas_schema_v2.sql)"), and seed v1's rollback line is replaced by "Forward-only: a correction is a new key in the next seed (schema v2 has one undo, valid only before seed v3)" (§10).
