## Existing tables reused, and what is new

- **Reused, unchanged:** the device workout log (`sports-genome-device-workout-history-v1`), the plan (`gym-optimizer-workout-plan-v1`), the exercise catalog (client code), `public.exercises` and `public.muscles` (referenced by foreign key from the new schema, never written). Workouts and sets stay on the device: no server table holds a bout, so there is **no exposure ledger table**; exposure is calculated on the device, on demand, from the same records Home, Review and Progress read (01-reconciliation.md, 04-database.md §2).

### Adding a production region

The schema, the calculator and the page's components take a second region as data (wave 0, 10-multi-region.md §9.2 gives the lanes and files of each later wave). What it takes, file by file:

1. **Its data**, in `shared/specialization/regions/<id>/`: `ids.ts` (its muscle ids and short names, 10-multi-region.md §1.2), `region.ts` (the region record: label, heading, entry label, sort order, body-map keys, `nodeForBodyMapKey`, `sides` with its side words and `onSideTemplate`, `catalogKeys` and `regionOnlyTagScope`, `wording` with the external heading, `measurementMetrics` and `measurementDefaults`), `nodes.ts` (its own nodes, home role), `members.ts` (every node it lists, its own and other regions', with order and caveats), `nodeActions.ts`, `claims.ts` (each with `ownerRegionId`), `mappings.ts` (its version, with `methodNotes`, mapping only its own muscles), `unmapped.ts` (tagged rows left unmapped, each with its reason), `variants.ts` (the library records its version maps, `variantsMappedBy`), `content.ts` (all of it but the drawing: what another region reads of it as a home), `diagram.generated.ts` and `index.ts` (the content with the drawing, composed with its homes' `content.ts` by `composeRegionData`, for the page). Records shared with other regions go in the shared libraries: `shared/specialization/actions/<id>.ts` (new joint actions only), `shared/specialization/sources/<id>.ts` (stable keys, one per URL), `shared/specialization/variants/<id>.ts` (one variant per catalog id, `cat-<id>`, with its counting attributes `sidedBy`, and `legLaterality` and `sideAnchor` where a leg region reads them). The drawing comes from the shared generator, `node design/specialization/shared/emit.mjs <id>`, with the region's config folder `design/specialization/<id>/` (`config.mjs`, `silhouettes.mjs`, `views/`, `evidence.mjs`; 08-diagram.md); `diagramContract.test.ts` holds every registered drawing. The logger reads no file of the region's own: it reads the generated logging table (step 2).
2. **The lists that name the production regions**:
   - `shared/specialization/regionIndex.ts`: the region record, for Home, Body Lab, Review, search and the page's region picker (they must not load the region's data);
   - `shared/specialization/registry.ts`: the full data, for the seed and the content tests;
   - `client/src/lib/specialization/loadRegion.ts`: one loader per production region, its own dynamic import, which the page calls when it shows that region (`loadRegion.test.ts` fails until the loaders match the index's production regions and the registry's data);
   - the generated logging table and hold list (`shared/specialization/loggingTable.generated.ts`, `holdCatalogIds.ts`): run `npx tsx scripts/specialization/emit-logging-table.ts` (`loggingTable.test.ts` fails until they match the registry; 07-logger.md).
3. **Catalog rows** for exercises the catalog does not have (`client/src/lib/exerciseCatalog*.ts`). A catalog exercise every region maps has one variant `cat-<id>`, in the shared library, so no two regions can describe it differently. An external member's home that has no page yet is a registered region with status `reference` (as `regions/upper_arm/region.ts` is until wave A promotes it): it lists its members and actions and takes no target; it needs no page words.
4. **Its seed rows**, in the next seed file: `npx tsx scripts/specialization/emit-seed.ts` writes the whole registry into `CURRENT_SEED_MIGRATION_PATH` (`emit-seed.ts`). Seed v2 is wave 0's own file; from the moment production records it, it is history, and the region's rows go in seed v3 (wave A) or later, never into an applied file (04-database.md §10–§11, `server/specializationHistory.test.ts`).

None of that changes a table, a column, a type, the calculator or a page component. The page takes a second region from the index and the loader (10-multi-region.md §6, 09-page.md "Several regions"): the heading becomes the region picker once there are two, the browser tab and search's way back name the page by the region's heading, search offers one destination per region (`specialization#<region>`), every side phrase comes from the region (`sideWordsFor`), and its measures are its own (`measurementMetrics`: circumference, grip force, and `girth_cm` for a girth around the trunk, in `MeasurementMetric` and schema v2's check). Still to come with a later region:

- **One published rule.** The calculator, the summary hook and "How this is counted" read `currentExposureRule` (`specialization_exposure_v1`), whose text speaks of grip and straps. Each wave publishes the rule version that first uses its clauses (v2 with the upper arm, 10-multi-region.md §4.3); `ruleClauses.test.ts` refuses production data that reaches an unpublished clause.
- **Content tests** (`forearmAnatomy.test.ts`, `forearmMappings.test.ts`, `forearmDiagram.test.ts`) check the forearm; a new region needs its own, beside the generic `regionContent.test.ts` and `diagramContract.test.ts`, which run over every registered region.

## Limitations, said plainly

- **No measurement of internal load.** Every number is a count of logged or planned work (bouts, reps, hold seconds) credited by reviewed mappings. Nothing here measures muscle force, activation or growth, and the page never says otherwise.
- **The anatomy review was automated.** Each claim was checked against web-search excerpts of reputable sources (NCBI StatPearls, peer-reviewed papers, university anatomy pages), not by a clinician; six function claims rest on a single StatPearls source. A human anatomy review is recommended before this is presented as settled (03-anatomy-evidence.md).
- **A published version is frozen with everything it rests on.** Once `forearm_mappings_v1` is in the database, its variants, node actions, reviewed claims (their basis included) with their sources, the cited sources, and each mapped muscle's review, region, role and catalog key cannot be edited, un-reviewed or deleted, and the seed refuses content that would (04-database.md §4). A correction from a later anatomy review becomes a new claim key and a new mapping version (`forearm_mappings_v2`), with the old rows kept readable.
- **No staging run.** The migrations were tested in PGlite (PostgreSQL 17.5), not in a staging project, because none exists; production (17.6) is the first server Postgres they run on.
- **The drawing is a schematic**, checked against the atlas's anatomy notes and standard descriptions, not against a medical illustration review; it is not a growth forecast and does not bulge.
- **History before this release** has no recorded arm, hold seconds or straps: one-arm work from before reads as "no arm recorded" (counted for neither arm), holds logged as reps read as "time not recorded".
- **Catalog rows 401–416** have no `public.exercises` row or Supabase exercise mapping yet, so lifts logged on them stay on the device (the strength sync counts them as unmappable) and they are not scored for strength rank.
- **Goals, measurements and exclusions live on the device** under the account's key; the database tables for them exist but nothing syncs yet.
- **Five draft mappings** ship in the published version, shown as pending review; once reviewed they belong in `forearm_mappings_v2`.
- **Offline before the page has loaded** shows the app-wide error screen, not an offline message (Release gates).
- **Long windows cost more.** A Custom window over a year of history takes a few hundred milliseconds per arm on the sandbox's CPU, and opening the page with a heavy year about a second or more (Release gates).
- **A second production region** is data for the schema, calculator and components (wave 0 made the tab title, search, the region choice, the side words and the measures region data); the one published rule's wording is still the forearm's until rule v2 ("Adding a production region").
- **Rules the owner may want to change:** a set logged in reps on an exercise now measured in seconds stays reps and is corrected in reps (07-logger.md); the published rule's text under "How this is counted" (`specialization_exposure_v1`) speaks of grip and straps on every region's page.
- **Two plan-editor edge cases:** on a hold, a target typed in the Plan editor that exactly matches a goal's rep default (for example "3 × 6–10") reads as that default, so it shows as "3 × 30 sec"; and a mid-workout swap of an exercise whose prescription varies by set ("3 × 10/8/6") starts the replacement's targets from the first planned set again (this predates the atlas; per-arm rows inherit it).
- **The smallest phones:** at 375 × 667 the selected muscle and the drawing's top are on the first screen in every state measured, Back with Custom dates included since wave 0 (Back in the heading row, the dates inline); at 320 × 568 the page fits without sideways scrolling but the drawing is below the first screen (09-page.md).
- **Phone checks** are headless Chromium emulating an iPhone (viewport, touch, device scale 3), not a real iPhone or Safari.
