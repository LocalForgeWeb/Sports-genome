# Sports Genome — Muscle Specialization Atlas
## Forearm-first implementation plan, data contract, and Supabase schema
**Prepared October 16, 2026 · Handoff to Claude**

## 1. Build this outcome

Build a specialization workspace that answers, for each forearm muscle:

1. Where is it, including depth and thumb-side/pinky-side orientation?
2. What movement does it produce?
3. What part of the visible contour might it contribute to?
4. Which of my planned and completed exercises load it?
5. How much of that exposure is direct dynamic work, deliberate isometric work, supporting work, or incidental stabilization?
6. What is missing relative to my own target?
7. Which relevant exercise can I add or swap into a specific training day?

The owner wants unusually developed forearms and granular control over high training volumes, including individual targets above 15 sets. Do not substitute a generic beginner routine or cap all targets at 15. Build the tools to inspect distribution and results. Do not encode “every additional set always causes more growth” as a biological guarantee. Volume, observed performance, and measured growth are distinct data.

Deliver functioning frontend, data mappings, calculations, migrations, seed content, and tests. A colored illustration without traceable workout integration does not satisfy this task.

**Scope:** Forearms first; anatomy nodes, actions, diagram assets, goals, and exposure calculations must support later specialization in deltoid heads, calves, upper back, and other regions through data additions.

**Current access limitation:** The current repository lookup did not return its schema. The SQL below is an explicit proposed extension, not a verified migration against the existing production database. Inspect existing tables and reconcile names/types/ownership before applying it. Reuse the existing Muscle Effect engine and workout records; do not build a disconnected second tracker.

## 2. Evidence model and useful limits

The 2025 dose-response meta-regression by Pelland and colleagues supports a positive volume–hypertrophy relationship with diminishing returns within the studied evidence. Its fractional set-accounting method fit the included data better than alternatives. That does not validate a precise fractional contribution for each small forearm muscle, establish an unlimited dose response, or prove that all named muscles need identical set targets. [S1]

Forearm rotation changes activation in some wrist muscles under controlled tasks. Therefore wrist position, grip, and forearm orientation belong in exercise variants. Those acute activation findings are not direct measurements of long-term muscle growth. [S2]

FDS components can be recruited selectively to some degree, with interdependence between fingers. This supports modeling finger actions, but not promising complete FDS/FDP isolation from ordinary gym exercises. [S3]

### Product rules

- [ ] Support user-defined targets; leave them unset until chosen rather than preloading “15 for every muscle.”
- [ ] Label target progress “of your target,” never “percent of optimal growth.”
- [ ] Keep exposure estimates, measured performance, and body measurements separate.
- [ ] Do not infer hypertrophy, recovery readiness, injury probability, or internal muscle force from set counts.
- [ ] Do not convert EMG percentage into a hypertrophy coefficient.
- [ ] Mark anatomical inference, experimental evidence, and product accounting choices distinctly.
- [ ] Allow a muscle to have anatomy content but insufficient exercise-mapping evidence.
- [ ] Never convert “unknown mapping” into “zero training.”
- [ ] No automatic volume increases merely because a tile is below target.
- [ ] Include brief optional performance/discomfort tracking so the user can evaluate whether their own higher-volume approach is working. Avoid a modal warning wall.

## 3. Anatomy catalog: do not collapse everything into “forearms”

The following is the content specification. Verify every production claim and attach sources before publishing. Physical-action summaries are anatomical; appearance descriptions are qualitative inferences from location and depth, not measured predictions of isolated hypertrophy. [S4–S8]

Use anatomical directions, not screen-left/screen-right. “Radial” means thumb side; “ulnar” means pinky side. A rotating forearm changes which surface faces the viewer.

| Node | Physical function to explain | Appearance note to develop | Display |
| --- | --- | --- | --- |
| Brachioradialis | Elbow flexion, particularly relevant with a neutral forearm | Prominent proximal thumb-side forearm contour; not a wrist flexor | Superficial, radial view |
| Flexor carpi radialis (FCR) | Wrist flexion and radial deviation | Superficial palm-side/radial flexor contour; not the entire thumb-side width | Superficial |
| Flexor carpi ulnaris (FCU) | Wrist flexion and ulnar deviation | Palm-side ulnar border contour | Superficial |
| Palmaris longus (PL) | Weak wrist flexion; tensions palmar aponeurosis | Small belly and long tendon; variable presence; not a major guaranteed width driver | Superficial, optional anatomy note |
| Flexor digitorum superficialis (FDS) | Flexes finger middle joints (PIP); contributes to grip | Intermediate flexor mass contributes to palm-side fullness | Intermediate |
| Flexor digitorum profundus (FDP) | Flexes finger end joints (DIP); contributes to grip | Deep bulk; cannot be drawn as an isolated surface stripe | Deep |
| Flexor pollicis longus (FPL) | Thumb end-joint flexion | Deep radial-side tissue; limited separately visible contour | Deep |
| Pronator teres (PT) | Forearm pronation; assists elbow flexion | Proximal palm-side oblique contour | Superficial |
| Pronator quadratus (PQ) | Forearm pronation; distal radioulnar stabilization | Deep distal forearm; little direct surface definition | Deep |
| Extensor carpi radialis longus (ECRL) | Wrist extension and radial deviation | Dorsoradial forearm contour | Superficial |
| Extensor carpi radialis brevis (ECRB) | Wrist extension and radial deviation | Dorsoradial extensor mass, partly covered | Layered |
| Extensor carpi ulnaris (ECU) | Wrist extension and ulnar deviation | Back/ulnar contour | Superficial |
| Extensor digitorum (ED) | Finger extension, especially MCP; assists wrist extension | Central dorsal forearm mass | Superficial |
| Extensor digiti minimi (EDM) | Little-finger extension | Small dorsal/ulnar component; not a major independent width lever | Superficial |
| Extensor indicis (EI) | Index-finger extension | Small deep dorsal component | Deep |
| Abductor pollicis longus (APL) | Thumb CMC abduction | Deep muscle with distal radial tendon course | Deep |
| Extensor pollicis brevis (EPB) | Thumb MCP extension | Small deep component; tendon visibility differs from belly growth | Deep |
| Extensor pollicis longus (EPL) | Thumb IP extension | Deep muscle; long dorsal tendon course | Deep |
| Supinator | Forearm supination | Deep proximal muscle; not directly visible in ordinary surface view | Deep |

Anconeus can be an adjacent elbow node, not a mandatory forearm hypertrophy target. Biceps and brachialis should appear as external contributors for curls/supination. Intrinsic hand muscles such as interossei and thenar muscles belong to a separate hand region; do not credit them as forearm bulk.

## 4. Exercise coverage: initial mapping queue

These are candidates to map to existing canonical exercises, not a prescribed workout or automatic seed of numerical coefficients. Use exercise IDs, not fuzzy name matching at runtime.

| Exercise family | Main mapping to review | Important distinction |
| --- | --- | --- |
| Supported wrist curl | FCR, FCU; PL supporting | Dynamic wrist work; finger flexors may hold the implement isometrically |
| Supported reverse wrist curl | ECRL/ECRB/ECU | Wrist extension, not simply finger extension |
| Resisted radial deviation | FCR/ECRL/ECRB contribution | Direction of external resistance and wrist angle matter |
| Resisted ulnar deviation | FCU/ECU contribution | Flexion/extension bias changes the task |
| Finger curl through finger motion | FDS/FDP, dependent on joint excursion | Finger movement must actually occur; distinguish from a wrist curl |
| Gripper closing | Finger flexors, shared | Dynamic closing versus a static gripper hold |
| Finger extension against resistance | ED and digital extensors, shared | Band setup may add finger abduction; do not treat all bands identically |
| Resisted pronation | PT/PQ | Shared pronator work, not proven exclusive PT or PQ isolation |
| Resisted supination | Supinator; biceps as external contributor | Elbow angle changes contribution; do not label supinator-only |
| Hammer curl | Brachioradialis; other elbow flexors | Finger gripping is a separate isometric exposure |
| Reverse curl | Brachioradialis and other elbow flexors | Wrist extensors often stabilize rather than perform dynamic wrist reps |
| Farmer carry / static loaded hold | Sustained finger-flexor demand; wrist stabilization | Intentional hold time, load, side, straps |
| Dead hang | Sustained grip demand | Bodyweight/assistance, grip style, and duration |
| Plate pinch | Thumb/finger flexors plus intrinsic hand contribution | Not equivalent to wrist-curl volume |
| Thumb flexion/extension/abduction variants | FPL / EPL-EPB / APL respectively, as reviewed | Small-muscle action coverage, not mandatory high-volume defaults |
| Rows, pulldowns, deadlifts | Incidental or meaningful grip exposure, depending on setup | Straps, handles, effort, and limiting factor affect interpretation |
| Wrist roller | Wrist action by direction plus grip | Direction-specific segments; not an indiscriminate “all forearms” exercise |

## 5. Counting model: make the numbers interpretable

### Independent dimensions

“Isolation” describes exercise organization/selectivity. “Dynamic” or “isometric” describes muscle action. They are not alternatives on one dropdown.

- Exercise organization: single-joint, multi-joint, task-based, mixed.
- Relationship: direct target, contributing mover, stabilizer, incidental, unknown.
- Muscle action: dynamic, isometric, mixed, unknown.
- Dynamic phase: concentric+eccentric, concentric-only, eccentric-only, unspecified.
- Dose: distinct bouts, reps, duration, external load and optional lever arm.

Use “Dynamic reps” in normal UI. A help note may explain that users often call this isotonic; ordinary free-weight movement does not imply constant muscle tension.

A reverse curl can be dynamic elbow-flexor work and approximately isometric wrist-extensor work in the SAME set. A global exercise-level action tag cannot represent this.

### Default muscle totals

1. **Direct dynamic bouts** — distinct completed work-set bouts mapped as direct dynamic work for this muscle.
2. **Other dynamic exposure** — contributing/shared work shown separately.
3. **Deliberate isometric bouts and seconds** — intentionally trained holds.
4. **Incidental grip/stabilization** — visible contextual exposure, not automatic full dynamic-set credit.
5. **Unclassified records** — explicit missing coverage.

“Bout” usually means an ordinary set. A drop set is one continuous bout containing several load segments. Show 1 bout / 3 drops or segments according to the existing terminology, plus reps at each load. Do not count it as three ordinary sets or assert it equals exactly one ordinary set's hypertrophic stimulus.

- [ ] Warm-ups, skipped sets, drafts, and deleted records excluded from completed work totals.
- [ ] Planned and completed totals calculated separately.
- [ ] Left and right tracked separately. Three bilateral sets mean three exposures per side, not six per side.
- [ ] A muscle counts a bout once within a category even when several segments/actions map to it.
- [ ] Mixed bouts report component durations/reps without silently double-counting the total.
- [ ] Multiple muscles can each have exposure from one bout; these are not shares that must sum to one.
- [ ] Region/session totals use distinct bout IDs, not the sum of muscle rows.
- [ ] RIR/RPE unknown remains unknown; never default to failure.
- [ ] Load × reps is external volume-load, not internal muscle force or equivalent hypertrophy.
- [ ] Carry seconds do not turn into “effective sets” with an invented conversion.
- [ ] A generic forearm mapping does not fan out into full credit for all 19 nodes.
- [ ] Existing broad forearm history stays “region-level only” until enough detail permits finer mapping.
- [ ] If fractional estimates are offered, make them an optional named/versioned accounting model; publish assumptions and preserve the raw totals alongside it.

### Worked accounting fixture — software test only

Two bilateral wrist-curl work bouts, two bilateral reverse-wrist-curl bouts, and three bilateral 30-second deliberate grip holds:

- Each arm has seven distinct work bouts across the session.
- Reviewed direct wrist-flexor mappings receive two dynamic bouts.
- Reviewed direct wrist-extensor mappings receive two dynamic bouts.
- Reviewed grip mappings receive three deliberate isometric bouts, totaling 90 seconds.
- Grip during the wrist exercises appears as contextual stabilization unless the mapping and recorded execution justify another classification.
- FCR and FCU both appearing in two bouts does not mean four distinct wrist-curl bouts occurred.
- No automatic claim that every muscle has received seven hypertrophy sets.

## 7. Recommendations and targets

Users can choose separate targets for direct dynamic bouts, deliberate isometric bouts, or hold duration. A goal for all exposure must not hide the distinction between dynamic and isometric work.

A target is user intent, not a validated growth threshold. Support values above 15. Do not auto-assign equal targets to PL, PQ, FDP, and brachioradialis merely because they are all named muscles.

- [ ] Targets attach to muscle or action, side, interval, and metric.
- [ ] Bilateral goal UI expands to explicit left/right targets for unambiguous comparisons.
- [ ] Display “Not targeted” rather than a deficit when no target exists.
- [ ] Recommendations explain a missing action or target gap, not just a muscle-name match.
- [ ] Rank candidates by reviewed target relevance, equipment, current exercise overlap, variant availability, and user preferences.
- [ ] Show additional muscles affected before adding an exercise.
- [ ] Preview how the proposed change affects planned totals only.
- [ ] Choose exact week/day and exercise slot before save.
- [ ] A swap changes future/uncompleted work; completed sets retain their actual exercise and variant.
- [ ] Do not recommend redundant exercises solely to increase a numerical score.
- [ ] Include “already covered by these exercises” so users can avoid needless duplication.
- [ ] If evidence cannot distinguish ECRL/ECRB selectivity, say so.
- [ ] “Missing muscle mapping” suggests fixing the mapping, not adding more training.
- [ ] Allow equipment and unavailable movements to be excluded.
- [ ] Offer a review of overlapping repeated exposures, using neutral factual wording rather than an invented recovery score.

### Proposed logical entities

| Entity | Key data / relationships |
| --- | --- |
| Region | Forearm, shoulder, calf; display order |
| Anatomy node | Canonical muscle/head/group, parent, region, layer, aliases, surface visibility |
| Joint action | Wrist flexion, radial deviation, PIP flexion, etc. |
| Muscle action | Node + joint action + role + evidence |
| Claim | Node + physical/appearance/selectivity statement + evidence state |
| Source / claim evidence | URL/DOI, locator, population/task, evidence type, review status |
| Diagram asset / diagram path | Versioned SVG + view/layer + node + path ID |
| Exercise variant | Existing canonical exercise + explicit execution dimensions |
| Variant muscle mapping | Node + action + relationship + muscle action mode + provenance |
| Exposure rule version | Published accounting policy and review metadata |
| Specialization goal | User + node/action + side + metric + dates + target |
| Derived exposure | User + source bout/segment + node + mapping/rule version + contributions |
| Optional measurement | User + side + circumference/performance + protocol/date |

Shared anatomy is read-only to ordinary users. Personal goals and measurements are owner-only. Derived exposures are writable only by the calculation service, not arbitrary client inserts.

### Proposed SQL skeleton

This is a concrete design template, not a production-ready standalone migration. The canonical *_key columns below MUST become foreign keys to verified existing tables, with matching types, or be replaced by existing relation columns. The application must not ship with unvalidated dangling keys. If a listed table already exists, extend it and map this design to it.

Use an unexposed schema for internal tables; expose narrowly through the existing authorized API or carefully configured invoker views/RPCs. Do not add this entire schema to the public Data API automatically.

```sql
create schema if not exists specialization;

create table specialization.regions (
  id text primary key,
  label text not null,
  sort_order integer not null default 0
);

create table specialization.nodes (
  id text primary key,
  canonical_muscle_key text, -- replace with real existing FK/type
  parent_id text references specialization.nodes(id),
  region_id text not null references specialization.regions(id),
  kind text not null check (kind in ('group','muscle','head','compartment')),
  name text not null,
  short_name text,
  aliases text[] not null default '{}',
  layer text not null check (layer in ('surface','intermediate','deep','mixed')),
  surface_visibility text not null
    check (surface_visibility in ('clear','partial','not_distinct','variable')),
  status text not null default 'draft'
    check (status in ('draft','reviewed','retired')),
  check (parent_id is null or parent_id <> id)
);

create table specialization.actions (
  id text primary key,
  joint text not null,
  label text not null,
  plain_description text not null
);

create table specialization.sources (
  id uuid primary key default gen_random_uuid(),

  title text not null,
  doi text,

create table specialization.claims (
  id uuid primary key default gen_random_uuid(),

  basis text not null check (basis in ('established_anatomy','experimental',

create table specialization.claim_sources (

create table specialization.node_actions (
  node_id text not null references specialization.nodes(id),

create table specialization.diagram_assets (

create table specialization.diagram_paths (

create table specialization.mapping_versions (

  method_notes text not null
);

create table specialization.variant_mappings (
  id uuid primary key default gen_random_uuid(),
  version_id uuid not null references specialization.mapping_versions(id),
  exercise_variant_key text not null, -- replace with real FK
  node_id text not null references specialization.nodes(id),
  action_id text references specialization.actions(id),
  relationship text not null check (relationship in
    ('direct','contributing','stabilizer','incidental','unknown')),
  muscle_mode text not null check (muscle_mode in
    ('dynamic','isometric','mixed','unknown')),
  evidence_basis text not null check (evidence_basis in
    ('anatomy','biomechanics','emg','longitudinal','inference','unknown')),
  rationale text not null,
  review_status text not null default 'draft'
    check (review_status in ('draft','reviewed','rejected')),
  unique(version_id, exercise_variant_key, node_id)
);

create table specialization.mapping_sources (
  mapping_id uuid not null references specialization.variant_mappings(id),
  source_id uuid not null references specialization.sources(id),
  locator text,
  limitation text,
  primary key(mapping_id, source_id)

create table specialization.rule_versions (
  id text primary key,
  specification jsonb not null check(jsonb_typeof(specification) = 'object'),
  published_at timestamptz,
  notes text not null
);

create table specialization.goals (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  node_id text references specialization.nodes(id),
  action_id text references specialization.actions(id),
  side text not null check (side in ('left','right')),
  metric text not null check (metric in
    ('direct_dynamic_bouts','deliberate_hold_bouts','deliberate_hold_seconds')),
  target numeric not null check (target > 0),
  starts_on date not null,
  ends_on date,
  period text not null check (period in ('calendar_week','rolling_7d')),
  timezone text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  check (num_nonnulls(node_id, action_id) = 1),
  check (ends_on is null or ends_on >= starts_on)

create table specialization.exposure_ledger (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  source_bout_key text not null, -- real FK; ownership verified
  source_segment_key text not null, -- real FK; same bout/user verified
  mapping_id uuid not null references specialization.variant_mappings(id),
  rule_version_id text not null references specialization.rule_versions(id),
  node_id text not null references specialization.nodes(id),
  side text not null check (side in ('left','right')),
  performed_at timestamptz not null,
  source_revision text not null,
  category text not null check (category in ('direct_dynamic','contributing_dynamic',
    'deliberate_isometric','incidental_isometric','mixed','unknown')),
  reps numeric check (reps >= 0),
  hold_seconds numeric check (hold_seconds >= 0),
  external_load_kg numeric check (external_load_kg >= 0),
  attribution_note text not null,
  calculated_at timestamptz not null default now(),

create table specialization.measurements (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  region_id text not null references specialization.regions(id),
  side text not null check(side in ('left','right')),
  measured_at timestamptz not null,
  metric text not null check(metric in ('circumference_cm','grip_force_n')),
  value numeric not null check(value > 0),
  protocol jsonb not null check(jsonb_typeof(protocol) = 'object'),

create index exposure_user_time

create index exposure_user_node_time

create index goals_user_dates

create index measurements_user_date
  on specialization.measurements(user_id, measured_at);
```

### RLS and access implementation

Follow the existing Supabase ownership model and official documentation [S9]. RLS and SQL grants both matter.

- [ ] Enable RLS on every table exposed through the Data API; use defense-in-depth for private personal tables.
- [ ] Ordinary users can read only reviewed/published reference content through the selected API.
- [ ] Ordinary users cannot modify shared anatomy, sources, mappings, or calculation rules.
- [ ] Goals/measurements have owner-only SELECT, INSERT, UPDATE, DELETE.
- [ ] UPDATE policies use both USING and WITH CHECK for owner protection.
- [ ] The ledger is owner-readable and service-generated; users cannot assign their own credited exposures.
- [ ] Avoid SECURITY DEFINER as a permission workaround.
- [ ] Use security_invoker views where supported; verify underlying schema privileges and RLS.
- [ ] No service-role key in the frontend.
- [ ] Grant only the needed schema/table/function permissions.
- [ ] If exposing RPCs, revoke unintended PUBLIC execution and verify caller ownership.
- [ ] Test cross-account access using real authenticated roles, not only an admin connection.

Owner-policy pattern, adapted to each personal table:
```sql
alter table specialization.goals enable row level security;
create policy goals_read on specialization.goals
  for select to authenticated using ((select auth.uid()) = user_id);
create policy goals_insert on specialization.goals
  for insert to authenticated with check ((select auth.uid()) = user_id);
create policy goals_update on specialization.goals
  for update to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);
create policy goals_delete on specialization.goals
  for delete to authenticated using ((select auth.uid()) = user_id);
```
This pattern alone does not expose an unexposed schema or grant table permissions. Configure access intentionally through the chosen app architecture.

## 9. Calculation API and cache contract

Authenticate on the server. Do not trust a request's user_id as authorization.

- Contributions with canonical exercise/variant IDs and source bout/segment IDs.
- Source data completeness and calculation timestamp.
- Region-level distinct bouts as a separate total.
- Unknown-side historical exposure separately, never silently duplicated to both arms.
