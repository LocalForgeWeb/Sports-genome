# Specialization atlas: the calculation (16 Oct 2026)

How exposure is counted, as implemented. The policy text is `exposureRuleV1` in `shared/specialization/rules.ts` (`specialization_exposure_v1`); the design is `02-design.md` §3–§5 and §8; this file says what the code does, where it had to choose, and which test holds each rule.

Since 19 Oct the calculator counts any region, not only the forearm (`10-multi-region.md`, lane 0b): sides are read per mapping, a node is credited by its home region's version, and goals read the rows. §9 says what changed and supersedes §1–§8 where they differ; the forearm's numbers are unchanged (§9.8, the golden test).

## 2. Rules as implemented

**Bouts.** A bout is one completed set (`isCompletedSet`) of a session with `status: "completed"`, or one planned set (`parseSetCount` of the prescription). Its id is the set's `id`, else `${session.id}/${exercise.id}/${index}` (index in the stored array); planned ids are `plan/${week}/${dayKey}/${entryId}/${n}`. A drop set is one bout; `stagesOf` gives its segments, each with its own load and reps. A duplicated bout id is read once.

**Exercise identity.** The recorded `catalogId`, else the exact catalog name (the tracker's rule: exact string, later row wins on a shared name), labelled "Matched by name". No fuzzy match. The variant read is `cat-<id>`, else the first variant listed for that catalog id.

**Load, reps, effort, holds.** Load is `setWeightKg` per segment from the unit it was typed in, shown as external load. Reps are the typed number per segment (blank or text is null). `effort` passes through; absent stays null, never "failure". `holdSeconds` (when the logger records it) goes on the first segment; zero, blank or text is null.

**Excluded.** Not credited and counted in `completeness.boutsExcluded`: `warmup: true`; `excluded: "not_completed"` (skipped sets, including the `skippedSets` stamp and fully skipped `notPerformed` exercises; typed-but-unlogged sets in finished workouts; logged sets of a workout still running). Removed workouts are simply absent.

**Window.** Completed mode: `mode === "completed"` and `performedAt` (the session's `completedAt`, else `startedAt`) in `[startAt, endAtExclusive)`; a null bound is open. Planned mode: `mode === "planned"` and `planWeek` equal to the interval's (all weeks if the interval has none).

**Arm** (as shipped on 16 Oct; since 19 Oct the side is read per mapping, §9.1, with the same numbers for the forearm). `bilateral` counts for both arms (3 sets are 3 per arm), `left`/`right` only for that arm, `unknown` only in `unknownSide` and `regionUnknownSideBouts` (work a draft mapping matched included: `unknownSide.pendingReviewBouts`, never either arm's `pendingReviewBouts`). A bout of the other arm is not read at all, not even for completeness. Side source: the set's recorded side (`left`, `right`, `both` → bilateral); else a variant with `laterality: "bilateral"`; else unknown. Planned work: bilateral variants are `structural`; `unilateral` and `either` variants are `bilateral` with `sideSource: "plan_assumption"` and the note "Each side assumed"; no variant is unknown. A planned set count on a one-arm (`unilateral`) exercise is per arm: "3 × 12" is 3 bouts on each arm. For an athlete with an active target the tracker builds the same plan as two rows per planned set, Right then Left, arm preset (`perArmSets`, 07-logger.md), and a swap or an add in the middle of a workout keeps that count in planned sets (two one-arm rows left become one two-handed set; a two-handed set left becomes a Right and a Left row of a one-arm exercise), so the plan logged as built, swaps included, gives each arm exactly its planned bouts. Without a target the tracker builds one row per planned set, and the athlete chooses each row's arm.

**Mappings.** Only mappings whose `versionKey` is the region's `mappingVersion.key` are read, and `rejected` ones are dropped, so an older generation left in the data never adds credit. The mapping version's own `state` (draft/published) is not gated on: review status gates credit; publication is the database's job. `reviewed` mappings credit; `draft` mappings show as `pendingReviewBouts` and a `notCounted` row ("Mapping pending review") when nothing reviewed credits that node in that bout. A bout with no arm recorded is kept apart here too: it adds to `unknownSide.pendingReviewBouts` on each arm's summary, not to the arm's `pendingReviewBouts`, and its `notCounted` row carries `side: "unknown"`, so no arm's "under review" total claims it (brief §9: unknown-side exposure is never duplicated to both arms). `unknownSide.bouts` stays credited work only.

**Category.** `categoryFor(relationship, muscleMode, variant.deliberateHold)` per mapping. Per node per bout: one category if every credited part agrees, else `mixed`, with every part listed in `parts` (in mapping-id order). Node buckets therefore never overlap.

**Straps.** A reviewed mapping with `requiresNoStraps` gives nothing to a bout logged `straps: "yes"`; the bout is listed in that node's `notCounted` with "Strapped: grip not counted" (and the note is added to any other credit the node gets from the same bout). With straps `unknown` the credit stands and the row says "Straps not recorded". `no` adds nothing.

**Totals per node.** `directDynamicBouts`/`Reps`, `contributingDynamicBouts`/`Reps`, `deliberateHoldBouts`, `deliberateHoldSeconds` (sum of segment seconds of `deliberate_isometric` bouts only), `incidentalBouts`, `mixedBouts`, `unknownBouts`. Seconds never become sets and reps never become seconds. `contributions` holds every credited row, unknown-side rows included (marked `side: "unknown"`), oldest first, then by bout id in natural order. `sharedWith` lists the other nodes with a reviewed `shared` mapping of the same variant in the same category.

**Coverage.** Per node, independent of the window: `reviewed` if any reviewed current mapping targets it, `pending_review` if only drafts do, else `none` (draw hatched; never zero).

**Region.** `regionDistinctBouts` counts distinct bout ids with credit on a node whose `regionId` is the region's, on this arm; external contributors (an upper-arm muscle in a forearm region) are credited on their own rows but do not make a bout region work. Work on an exercise with no mapping in the region whose catalog tags (primary or secondary) include a target node's `catalogMuscleKey` goes to `regionUnclassified` and never to a node. A mapping to a compartment node credits the compartment only. Each region total keeps the set records it counts, so the page can open it down to the set (brief §1, §9 source bout ids): `regionBoutRows` (one per distinct bout behind `regionDistinctBouts`), `regionUnknownSideRows` (behind `regionUnknownSideBouts`) and `regionUnclassifiedRows` (behind `regionUnclassified.bouts`, each naming its exercise), all oldest first, then by bout id. A row is a `RegionBoutRow`: bout id, side and where it came from, catalog id, name and how it was matched, session id and label, time, kind and segments; it carries no node and no category, because a region total is distinct bouts, not credit to a muscle. The rows are an addition: no count is made from them.

**Completeness** is scoped to the region and to bouts that could reach this arm (this arm, bilateral, unknown): `boutsConsidered` = reviewed + pending-only + region-only (a partition), plus name-matched, unknown-side and the exclusions.

**Goals.** Only goals of this region and arm, active today in their own zone. Completed mode reads each goal over its own period relative to `now` (calendar week or rolling 7 days in the goal's zone), not the window on screen; planned mode reads the plan week shown. A muscle goal's value is that muscle's bucket for the metric (`direct_dynamic` or `deliberate_isometric`; seconds summed), so it equals the number on the muscle's row. A movement goal counts distinct bouts in which a credited reviewed mapping with that action, on a region node, has the metric's category; seconds once per bout. Unknown-side bouts never count. `fraction` is unbounded; `label` is "N of your T" ("… seconds" for hold seconds). No goal, no row: nothing reads as a deficit.

**Determinism.** `calculatedAt` is the request's `now`. Nodes are in region order; contributions by time then natural id; region-only exercises by bouts then name.

## 3. Windows

Calendar week: Monday 00:00 local to the next Monday 00:00 local, end excluded; 167 or 169 hours across a clock change. Rolling 7 days: exactly 168 hours back from now, end excluded. Custom: two local dates, both included (a reversed pair is read in order). Local midnight is found, not assumed: a date with no 00:00 (Havana 8 Mar 2026, Santiago 6 Sep 2026) starts at 01:00; a repeated midnight (Havana 1 Nov 2026) starts at the first one. Plan week: no dates, label "Plan Week N, as written".

## 4. Cache key

`useSpecializationSummary` memoizes in a module LRU (24 entries) keyed by `summaryCacheKey`: account scope, region, interval (kind, start, end, plan week), time zone, arm, mode, plan revision (planned mode only), source revision (completed mode only), rule version, mapping version, a fingerprint of the goals, and `now` to the minute. A completed summary carries no plan revision and a planned one no source revision, so logging a set never recalculates the planned view and a plan edit never recalculates the completed one. The workout log is re-read on `sports-genome:device-workout-history` and on a `storage` event for its key (another tab); every log, edit, removal, swap or late offline record changes the source revision. One call computes every node: there is no request per muscle.

## 5. Suggestions

`recommendFor` (`recommendations.ts`) follows `02-design.md` §8; the comment at the top of the file says the same.

**Candidates.** Exercises with a reviewed current mapping to the selected node (or, for a movement, to the selected action on one of the region's muscles) that the counting rule credits as work. Relevance is read through `categoryFor(relationship, muscleMode, variant.deliberateHold)`, the calculator's own table: a `direct` mapping credited as direct dynamic is "direct dynamic", a `direct` mapping credited as a deliberate hold or as mixed is "direct hold", and a `contributing` mover's credited work is "contributing". Work the calculator files as incidental (an isometric mapping on an exercise that is not a deliberate hold, such as the contributing finger grip in Towel Pull-Up and Rope Climb), steadying (`stabilizer`) or unknown is never a candidate and never "already covered by". One candidate per exercise variant, at the best relevance its credited mappings give. Draft mappings never produce one: a node or action with no reviewed mapping returns `mapping_not_reviewed`.

**What a candidate counts toward.** A muscle target takes a set only when that set's work on the muscle is the target's kind (direct dynamic for dynamic bouts, a deliberate hold for hold bouts and hold seconds); a set that loads the muscle two ways counts as `mixed`, for neither; a movement target reads each reviewed mapping for that movement on a region muscle. `targetGap` is the first unmet target the exercise counts toward that way (null when none). A test checks, for every muscle, movement and metric of the forearm and the synthetic region, that an exercise claims a target exactly when one logged set of it raises that target in `getSpecializationSummary`.

**Ranking**, in order:
1. it counts toward one of the athlete's unmet targets for this (`targetGap`);
2. it is direct work on one of the muscle's main (prime) actions that had no direct work in the window, when the muscle had direct work on this arm on another action (`missingActions`). Work with no arm recorded, or a set counted as mixed, is not in the arm's direct count, so on its own it never makes an action "missing" next to "it has no direct work in this window"; direct work on any side does cover its own action;
3. relevance: direct dynamic, then direct hold, then contributing;
4. equipment in the athlete's profile (`equipmentMatchesProfile`; no profile means all available);
5. overlap: already in the plan week, or, in completed mode, already logged in the window on this arm or with no arm recorded (`alreadyPlanned`, `alreadyLogged`, `loggedBouts`), ranks lower;
6. one-arm work first when the selected arm trails the other on the goal's metric (else on direct bouts);
7. name, then catalog id.

**Left out.** Exercises and equipment the athlete excluded are removed and counted (`excludedCount`). An exercise that counts toward no unmet target is not suggested when its kind of work has every target met or when it counts toward a met one (`skippedAtTarget`): with a dynamic target met and a hold target not, only work that is not direct dynamic is offered. Contributing dynamic work (a helper moving through range, `contributing_dynamic`), which counts toward no target, stays, below the work that does; a contributing deliberate hold counts toward a hold target like a direct one. A node or movement with every target met returns `at_target` with a neutral note ("… already has 12 of your 10 direct dynamic bouts this week. Nothing is suggested to add more.") and its covered list, and no candidate.

**What is said.** Each candidate has one plain `why`: the missing main action first when it fills one ("Ulnar deviation: no direct work in this window."), then the work and the gap it can fill ("Direct wrist extension for extensor carpi ulnaris; 2 of your 10 direct dynamic bouts this week"); with targets it cannot fill, that plainly and why when the reason is the kind of work ("not a hold, so it does not count toward your target of 3 deliberate hold bouts this week", "a hold, so …", "one set of it loads this muscle two ways, so it counts as mixed work, …"); with no target, the work the muscle already has. Then shared allocation, the arm, "Already in this plan week.", "Already logged in this window: N sets" (with "with no arm recorded" where that applies) and missing equipment. A "why" never claims a gap the exercise cannot fill. `alsoLoads` lists every other node its reviewed mappings credit, external contributors included. On the result:
- `targetNote`: an unmet target that no reviewed exercise can count toward at all, said plainly once ("No reviewed exercise for flexor carpi radialis counts toward your target of 3 deliberate hold bouts this week."); a candidate whose only gap is such a target says "it counts toward none of your targets here";
- `missingActions`: the muscle's main actions with no direct work in the window, when another action had some (rule 2); `missingActionNote` in `components/specialization/model.ts` says, for one no candidate covers, why nothing is offered;
- `emptyReason`, only when there is no candidate, naming every cause and only a true one, after the `targetNote` when there is one: every exercise left out by the athlete ("Every reviewed exercise for this is left out by your choices under What is suggested."), every one answering a met target ("The exercises that train this answer a target you have already met. Nothing is suggested to add more."), both ("The exercises that train this either answer a target you have already met or are left out by your choices under What is suggested."), or, with nothing to offer at all, "No reviewed exercise trains this directly or as a main helper yet.";
- `alreadyCoveredBy`: the plan week's exercises and, in completed mode, those logged in the window on this arm or with no arm recorded, that load the target as credited work (incidental holding is not "covered"), by name, each with its plan days and then one `days` entry keyed `logged` ("4 sets logged in this window", "2 sets logged in this window, 1 with no arm recorded"; `coveredWords` in `model.ts` says it as words, never as a day), its category and `loggedBouts`.

`previewPlannedChange` runs the calculator in planned mode on the before and after plan bouts and returns only the nodes whose values move, with the region total; completed bouts handed to it are ignored.

## 6. Where the design left room, and what was chosen

- **Types.** Optional fields were added to `types.ts`: `ExposureBout.excluded?: "not_completed"` (so completeness can count what the adapters left out without the calculator reading storage), `NodeExposure.notCounted?: Contribution[]` (the ledger rows for strapped grip and pending mappings, which earn nothing and so have no place in `contributions`), `NodeExposure.unknownSide.pendingReviewBouts?` (17 Oct, final review: no-arm work a draft mapping matched, kept off both arms' `pendingReviewBouts`; always set by the calculator), and, on 17 Oct, `SpecializationSummary.regionBoutRows?`, `regionUnknownSideRows?` and `regionUnclassifiedRows?` (`RegionBoutRow[]`, the set records behind the region totals, §2 "Region"). They sit beside `regionUnclassified` rather than inside it, so its shape, and every reader of it, is unchanged.
- **Region-only work and arms.** `regionUnclassified` lists this arm's, two-handed and unknown-side records: unmapped exercises have no variant, so their history is almost always unknown-side, and leaving it out would hide it. It is never added to a node or to `regionDistinctBouts`.
- **Mixed bouts and goals.** A goal reads the bucket strictly: a `mixed` bout is not counted toward a direct-dynamic or hold goal, so the goal and the row always agree. Hold seconds of a mixed bout are visible on its ledger row only.
- **Planned targets.** Reps and seconds read the low end of a range ("8–12" → 8, "20–30 sec" → 20 s): what the plan commits to. "m" is metres, not minutes. A bare number on an exercise measured in seconds is seconds ("3 × 40" on a hang is 40 s), as the set card reads it. An entry with no saved prescription reads the training goal's default for its position (`getGoalPrescription`), as the weekly review, Today and the tracker do, when Home passes the goal; otherwise 3 sets. On an exercise measured in seconds the default is a hold's: the goal's set count for that place with a 30-second target ("4 × 30 sec" where the goal says "4 × 3–6"; "3 × 30 sec" with no goal), and a saved prescription that is any goal's default for any place (the text the planner pins when it builds a day or a week) is read the same way, so planned hold seconds are never a rep range. Set counts are unchanged, so the planned bouts, the weekly volume map, Today and the week review count the same sets. Home's Plan editor, print and share read the same function with the measure from `shared/specialization/holdCatalogIds.ts` (07-logger.md, "One reading of a hold's prescription").
- **Shared allocation.** Grouped by variant and category, not by action: the two deep finger flexors bend different joints but share one grip, while a set's shared dynamic work stays apart from shared holding in the same set.
- **Contributing candidates.** Included as the last tier, as the design's ranking lists it; "direct" in "a reviewed direct mapping" is read as "mapped to the selected node".

## 8. Known limits

- History logged before this release has no `side`, `holdSeconds`, `warmup` or `straps`: it reads as no arm recorded (except two-handed variants, which count for both arms), holds as "time not recorded" (a hold bout with no seconds; the recap, the session detail and an exercise's history say "Seconds not recorded"), no warm-ups and unknown straps. A set with reps on an exercise now measured in seconds stays a rep set: its reps are never read as hold seconds (07-logger.md). The logger keeps all four from this release on (`normalizeSet`, `loadDeviceWorkoutSessions`; 07-logger.md).
- `DiagramViewId` is the drawing's own id (any `^[a-z][a-z0-9_]*$`), and each drawing lists its views with their words in `viewOrder`: the forearm's palm, back and thumb side, the deltoid fixture's front, side and rear (02-design.md §10). The calculator reads no view.
- Planned bouts have no load, and an assumed side for one-arm work; the ledger says so. With a target, the tracker lays the same plan out per arm, so the assumption is the rows the athlete is offered.

## 9. Several regions (19 Oct 2026)

What lane 0b of `10-multi-region.md` (§9.2 there) changed in the calculator, its adapters, goals and stores, in that note's order. The rule stays `specialization_exposure_v1` through wave 0.

### 9.1 Sides, read per mapping (note §2.1)

- **A bout carries sides, not a side.** `ExposureBout.armSide` and `legSide` are each `{ side: left | right | both, source: recorded | plan_assumption }` or null: the set's `side` and `legSide` exactly as stored (an older import's `bilateral` is read as `both`). The adapters no longer settle a side from the variant (`sideOf` went; `recordedSidesOf` reads the two fields), so one bout list serves every region and `SessionBoutDeps.variants` is no longer read.
- **`nodeSideFor(region, variant, mapping, bout)`** returns the sides one mapping's work is counted on, by the note's six rules: (1) a midline region, once, `midline`; (2) a mapping with `sideRelation: both`, each side; (4) a side recorded for the region's limb, that side, the other one for an `opposite` mapping, each side for Both; (3) a variant two-sided by definition for the region's limb (`laterality` for the arm, `legLaterality` for the leg), each side; (5) a variant `not_applicable` for the region's limb, no side; (6) anything else, a side recorded only for the other limb included, unknown. It also returns the recorded side it read (the region limb's, else the other limb's), how the side is known and the rule's branch (§9.7). A bout no mapping speaks for (region-only or unrelated work) is read with relation `same` and without rule 5, which is about mappings: a limb the exercise does not use gives it no side by rule 6.
- **Rule 4 before rule 3.** The note's rule 3 counts a two-handed exercise on each side "as today", and today, as the forearm shipped, a side recorded on a two-handed exercise counted on that side alone; the note's §4.3 allows the forearm no other change at wave 0. So a side recorded for the region's limb is read before the exercise's own two sides. Only an import or a swapped exercise can put a side on a two-handed exercise (the logger does not ask there); the golden edge week holds such sets (§9.8). Read in the note's printed order, 546 of 4,992 catalog-wide forearm summaries differed from the shipped ones (every two-handed exercise logged with one arm, §9.8); read in this order, they equal the shipped ones but for the §8 rows.
- **A node on one side.** For a summary's side S a node shows its credited mappings counted on S, as one contribution; else those with no side, as one contribution kept apart (`unknownSide`); else, with nothing credited, its strapped mappings that apply on S, else its strapped ones with no side, then the same for its pending ones. Work counted only on the other side shows nothing on S.
- **What a row says.** Every contribution carries `countedSide` (S, `midline`, or `unknown`), `recordedSide` (`{ limb, side, source }` or null) and `sideRelation` (its first part's where its parts differ); every region row carries `countedSide` and `recordedSide`. The ledger can now say "Right" with "Left hand: opposite side". `side` and `sideSource` stay as the summary's single reading for the readers that have not moved to `countedSide` (lane 0d): `unknown` for a row kept apart, `bilateral` for a row counted on both sides, on the midline or on a plan's assumed sides, else the one side; for the forearm they read exactly as before.
- **Region totals and completeness.** A bout is in `regionDistinctBouts` on S when one of the region's own nodes counts it on S, and in `regionUnknownSideBouts` only when none does and one has it with no side, so no set is in both. A midline region counts every bout once and has no unknown-side set. Completeness reads the own nodes' mappings in the order a node row does: credited, then strapped, then pending; the first kind that has the bout on S or with no side decides. The bout is considered on S when any kind does; it is in `boutsUnknownSide` when the deciding kind has it with no side; it counts in `boutsWithReviewedMapping` when credited or strapped work decides, else in `boutsPendingReview`. So completeness agrees with the totals: a set kept apart with no side is in both the unknown-side set and `boutsUnknownSide`, and a set that only a draft mapping puts on S is under review there, not reviewed (one-arm row logged Right, the lat reviewed, the erectors a draft loaded on both sides: on the left it is under review). For the forearm, whose mappings of one exercise all read a set alike, this is the 16 Oct reading. A request whose side does not fit the region (left or right on a midline region, `midline` on a paired one) throws.
- **Region-only work reads the shared library.** A bout no own mapping speaks for is read with the region's variant for the exercise, else the shared library's (`variantFor`, note §3). Through wave 0 the library is the forearm's 119 variants, all mapped by the forearm, so no number moves; each later release lists the region-only sets its new two-handed variants move from "no arm recorded" to both arms (note §4.3, decision 11c).

### 9.2 One-sided work is planned per side (note §2.1)

`boutsFromPlan` reads each exercise's `sidedBy` limb and the variant's laterality for it: done one side at a time, a planned set is two bouts, `…/n#right` then `…/n#left`, each with that side on that limb and `source: plan_assumption`; done either way, one bout recorded `both`, `plan_assumption`, as the tracker logs it (one row starting on Both); anything else, one bout with no side, which the calculator reads from the exercise. A segment carries its bout's id. "3 × 12" on a one-arm exercise still gives each arm 3 bouts and the note "Each side assumed"; a midline page now counts that plan as the tracker logs it, 6. The page lays the plan out by `planningVariantsFor(region)`: the region's own variants, then the shared library's for every exercise the region has none of, which is how the calculator reads an exercise (the region's variant, else the library's). The hook, the add and swap preview and the golden test all use it, so the preview's "before" equals the planned page and a variant a later release adds to the library shows in the golden test as it shows on the page.

### 9.3 A bout is classified by the region's own muscles (note §4.2, §8)

- **mapped**: one of the region's own members has a current mapping (reviewed or draft) for the variant; every member's credited work is recorded, external ones included.
- **region-only**: no own member is mapped and the catalog tags carry the region's catalog keys within its tag scope: counted in `regionUnclassified` and `boutsRegionOnly`, never fanned out to own nodes, while an external member's credit still shows on its row.
- **external-only**: no own member is mapped, the tags do not match, and an external member is mapped: credited on the external row only, in no region total and not in completeness.
- **unrelated**: nothing above.
- `boutsWithReviewedMapping` and `boutsPendingReview` read the own members' mappings only.
- Catalog keys and tag scope come from the region record (`catalogKeys`, `regionOnlyTagScope`: `any` reads primary and secondary tags, `primary` primary tags only), not from the target nodes; the forearm's `["forearms"]` and `any` are what it derived before.
- **What is not counted is shown.** `completeness.boutsListedUnmapped` and `listedUnmappedRows` (a region row with `tag: secondary | listed` and the listed `reason`, null where none is listed): sets in the window, not warm-ups and not excluded, on S or with no side, of an unrelated or external-only bout whose exercise tags the region only as a secondary muscle where the region reads primary tags, or is one of the region's listed unmapped exercises. An external-only set is in none of the region's totals, so it is listed too, with `creditedTo`, the external members whose rows show it on S (empty for an unrelated set): a home region's mapping (the back's quadratus lumborum on a deadlift, listed by the core) never takes a set off the core's list, and the page can say where it is credited. The forearm reads tags at any scope, so its list holds only the listed exercises it is not tagged with (the sled push, drag and sprint, 296–298); the golden histories have none.

### 9.4 The home region speaks for its muscles (note §4.1, §4.2)

`indexRegion` credits each node by exactly one version (`creditedBy`): a node of the region by the region's current version (`version.own`); an external member by its home region's current version, restricted to the region's members (`externalMappingVersions`, `version.home`); and, where the home has published none, by the listing region's own rows (`version.listing_fallback`). Through wave 0 that is the forearm's 53 rows on the biceps and brachialis, read as before. Where two versions meet, a mapping's key is `mappingKeyIn(region, mapping)`: its id within the region's own version, `<version>/<id>` for another version's, so the forearm's ledger keys are unchanged; `mappingsByKey` reads them back (the page's `mappingsBehind` still looks keys up in `data.mappings`, which holds the own version only; lane 0d's to change). `sharedWithOf` groups shared mappings only within one version: a version makes no claim about another's muscles.

### 9.5 Goals read the rows (note §2.2)

- **Progress** is counted from the same per-node, per-side contributions as the rows, over the goal's own period: a muscle goal counts the node's contributions counted on its side whose category is the metric's (seconds summed), which is the row's bucket; a movement goal counts distinct bouts with a contribution of an own node counted on its side whose part is that movement and kind of work, seconds once per bout. `onArm` went. A test holds every target equal to its row in every scenario of §9.9.
- **`validateGoal(goal, existing, scope?)`.** The side must fit the region: left or right in a paired region ("Choose the left or the right leg. A target for both legs is saved as two."), `midline` in a midline one ("This region is counted as a whole, with no left or right. Save the target without a side."). The words are the region's (`wording.sideWord`): the scope's region, else the registered index's, else "side". The clash names "a right-leg target" ("a target" on the midline). With the page's scope (`goalScopeOf(data)`: the region and its target nodes), a new muscle goal must name one of the region's target muscles, and a goal already saved on any other muscle may only be ended: an end date set or brought forward, nothing else changed but `updatedAt` ("Targets are for this region's target muscles. You can end or remove this one."). Without a scope, as an older caller, only the fields are checked; the page passes it to the store's `save(goal, scope)`.
- **`sameGoalTarget`** compares a muscle goal by its muscle, not its region: a muscle has one home, so a re-homed target and one saved on the home page are the same target.
- **Re-homing on read.** `rehomedGoal(goal, homeOf)` reads a muscle target saved on another region's page (`<home>.<slug>`, note §1.2) as a target of the muscle's home region, with the same id, once that region is in production; until then it counts where it was saved. A target whose side the home cannot hold stays where it was saved (`sideFitsRegion`): a core target on the back's quadratus lumborum has side `midline`, which matches neither of the back's sides, so read as the back's it would show on no page and could not be ended; left on the core, it stays a target the core page can end. The goal store applies it when it loads, with the registered index's records (`regionIndexEntry`), so the next save writes it so. Through wave 0 the upper arm is a reference region, so nothing moves.
- `goalsForBothSides` splits Both into two targets (`goalsForBothArms` is kept as its alias).

### 9.6 The device stores keep what they cannot read (note §2.1, §4.4)

Targets accept side `midline`. Measurements accept `midline` exactly for `girth_cm` (a girth goes around the trunk) and left or right for every other measure, and the postures `arm_flexed` and `standing_relaxed`. An entry either store cannot read is left out of what the screens see and written back, untouched, after the readable ones on every save and removal, so a later version's target or measurement survives this one.

### 9.7 Rule versions (note §4.3)

`publishedExposureRules` holds v1 only, and `currentExposureRule` is v1. A summary records the rule it was given (`SummaryRequest.rule`), else the current one; the hook's cache key reads the current one. `ruleClauses` names, for every branch of the calculator (`nodeSideFor`'s rules per limb, a planned set per side per limb, `indexRegion`'s three choices of version, the four classes of bout, the two tag scopes), the rule that publishes it: a key of v1's text, or the planned words of v2 (a home region's credit, classification by own muscles, a primary tag scope), v3 (side relations), v4 (midline) or v5 (the leg limb, a limb the exercise does not use). `ruleBranchesOf(data)` lists the branches a region's data can reach: through each mapping that credits a node (an `opposite` mapping on any variant, since a recorded side is read first; a `not_applicable` variant where the mapping is not `both`), and, for a set no mapping speaks for, only the two-sided, recorded and unknown branches every paired region lists, or the midline. A test reads every variant of every registered and fixture region and of the shared library, plus a hands-free one (200), through `nodeSideFor` with and without each credited mapping and every recorded side, and requires each branch reached to be listed; so a region-only set of a hands-free exercise a later library adds keeps the forearm on v1. A second test refuses production data that reaches a branch of an unpublished rule, and shows that each fixture region is covered once its wave publishes its rule. `exposureCategoryLabelsFor(wording)` names incidental work in the region's word ("Incidental bracing / stabilization"); for the forearm it equals `exposureCategoryLabels`.

### 9.8 The golden test

`golden.test.ts` computes the release-gate histories with this code and compares them with the code the forearm shipped with (6738eeb): summary-cost.ts's year at 4 workouts a week and its heavy year (6 a week, sets × 2.5), page-cost.mjs's week, page-offline.mjs's workout, and one week of edge cases (Both, one arm and none on an either-way exercise, one arm and Both on a two-handed one (132), warm-ups, skips, straps yes, no and unknown, a drop set, a name match, holds, region-only work, an unfinished workout, a skipped-sets stamp, a skipped exercise), each in three windows for both arms, and the release-gate plan and the four day templates as a plan for both arms, laid out as the page lays them out (`planningVariantsFor`; the shipped tree, which has none, used the forearm's variants): 34 summaries, with 18 targets on muscles, movements, the biceps and the anconeus. The reference (`__fixtures__/goldenSummaries.6738eeb.json`) was written by `scripts/specialization/release-gates/golden-summaries.ts` run in a fresh `git archive 6738eeb` copy outside the repository; 14 summaries (those of 90,000 characters or fewer) are kept whole, 20 as their totals and the SHA-256 of their canonical JSON. The summaries are identical but for these allowed differences, which the test checks are where they belong:

1. planned bout ids of one-sided variants, `…/n#right` and `…/n#left` (the day-templates plan's 46, 410 and 411, each on its own arm's summary);
2. the new `countedSide`, `recordedSide` and `sideRelation` fields, each checked before it is set aside: `countedSide` is the summary's arm unless the row is kept apart; `recordedSide` is the arm's side as the set or the plan gave it (a split planned bout's own side, Both for an either-way plan), null where the side came from the exercise or is unknown; `sideRelation` is `same`;
3. the new §8 fields `completeness.boutsListedUnmapped` and `listedUnmappedRows`, zero and empty on every one of these histories.

Beyond the test, a catalog-wide differential (every catalog exercise with no side, left, right, Both and an older import's `bilateral`, straps unset, yes and no, a warm-up and an unfinished set, completed and planned, both arms, the 18 targets: 4,992 summaries) gives the shipped summaries but for the §8 rows of 296–298 (36 summaries), and the forearm's performance series equal the shipped ones.
